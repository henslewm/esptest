## 2026-10-04 — Milestone 3 complete: BLE HID keyboard paired + typing confirmed (hardware-confirmed)

- Completed Milestone 3 (BLE keyboard link): implemented `src/ble_keyboard.{h,cpp}` with the bundled Bluedroid BLE HID stack (`BLEHIDDevice`, keyboard-only input report — avoids the core-3.3.12 NimBLE duplicate-UUID bug), wired into `src/esptest.ino`; updated `src/MODULES.md`. The board advertises as BLE HID keyboard "esptest-BLE-KB" (BLE address d4:05:92:46:94:25 = base MAC +1) and bonds with Windows via Just-Works / ConfirmOnly. Operator-confirmed: the device paired and typed its line into Notepad; three HID keyboards now enumerate OK (USB, Logitech K780, our BLE). Once bonded, Windows auto-reconnects with no input (satisfies the "no user input" steady state for BLE). `pio run -e dev` SUCCESS, flash 21.5% of the 3MB app partition. App ELF SHA-256 = f380eb4ce7ddceaaffb0c43320a25ddaff0d8eb4b2ee9491f9939b90c35f11bb.
- Incident + resolution: the first BLE build advertised aggressively (default 20-40ms interval, full TX power) and its 2.4GHz activity knocked the user's Logitech M720 Triathlon BLE mouse offline. Root cause confirmed by correlation — the mouse would not reconnect while the board's BLE was live and reconnected the instant the board BLE was silenced. Mitigations applied in `ble_keyboard.cpp`: `BLEDevice::setPower(ESP_PWR_LVL_N3)` (lower TX power), advertising interval ~200-250ms (`setMinInterval 0x0140` / `setMaxInterval 0x0190`), and advertising stops on connect (`onConnect`). The gentle build was reflashed and pairing then succeeded without repeating the interference. Host-side helper scripts (`reconnect_mouse.ps1`, `ble_scan.ps1`, `find_ble.ps1`, `pair_esp.ps1`, `pair_by_id.ps1`, using Windows WinRT BLE APIs) live in the session scratchpad.
- Recorded `DECISIONS.md` ADR-005 (Bluedroid BLEHIDDevice, keyboard-only, Just-Works/ConfirmOnly) and ADR-006 (good-2.4GHz-neighbor BLE settings after the mouse-interference incident); added `RISK_REGISTER.md` R-009 (BLE advertising interference with nearby 2.4GHz/BLE peripherals); closed OL-009 and added OL-011 (refine click-free scripted first-pair ConfirmOnly handler; low priority — auto-reconnect covers steady state). OL-010 (Milestone 4 timestamp/test.txt workflow) stays open.
- Known refinement: the fully-scripted first-pair ConfirmOnly handler returned "RejectedByHandler" in one attempt; the bond still completed (likely via a Windows confirm). A click-free scripted first-pair handler (GetDeferral + Accept) is a follow-up (OL-011); auto-reconnect already covers the steady-state no-input requirement.
